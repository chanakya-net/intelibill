# P04-06 stock intake and recovery

Single intake, each new bulk manifest, and each new bulk row require current `NewTrading` access. The server checks live session and Owner or Manager membership. The posting transaction takes the account and shop licence locks before the period, expiry and stock locks. It reevaluates the fenced decision after potentially blocked saves, including the keyed receipt completion. A row's `performedAt` selects its business date. The server clock determines access.

A keyed bulk submission may commit one row while rejecting another. The manifest freezes the ordered row identities and hashes. An authorized retry sends the original `POST /api/inventory/inbound/batch` with the same key, rows, order and timestamps. It recovers committed outcomes under `Recovery` and checks current trading access for uncommitted rows. There is no separate outcome lookup for bulk intake.

For a two-row submission crossing the deadline, the merchant receives HTTP 207 with `succeeded[0].clientRowId` set to A, `result.inventoryBatchId` and `result.stockTransactionId` identifying the immutable posting, and `failed[0].clientRowId` set to B with `errors[0].code` equal to `Licence.Expired`. This expiry refusal has `retryable: false`. A fresh key at expiry receives HTTP 403. An authorized resend with changed or reordered rows receives HTTP 409 `Operation.PayloadMismatch`. Revoked authority or security suspension withholds the outcome and the hash comparison. An unconfirmed response leaves the original key recoverable.

Generic gains and unrelated adjustments remain classified as `GeneralStock`. Correction labels do not change that action. Source receipt corrections continue through their existing `SourceCorrection` endpoint and source eligibility rules.
