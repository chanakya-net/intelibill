# P04-06 stock intake and recovery

Single intake, each new bulk manifest, and each new bulk row require current `NewTrading` access. The server checks live session and Owner or Manager membership. The posting transaction takes the account and shop licence locks before the period, expiry and stock locks. It reevaluates the fenced decision after potentially blocked saves, including the keyed receipt completion. A row's `performedAt` selects its business date. The server clock determines access.

A keyed bulk submission may commit one row while rejecting another. The manifest freezes the ordered row identities and hashes. An authorized retry sends the original `POST /api/inventory/inbound/batch` with the same key, rows, order and timestamps. It recovers committed outcomes under `Recovery` and checks current trading access for uncommitted rows. There is no separate outcome lookup for bulk intake.

For a two-row submission crossing the deadline, the merchant receives HTTP 207 with `succeeded[0].clientRowId` set to A, `result.inventoryBatchId` and `result.stockTransactionId` identifying the immutable posting, and `failed[0].clientRowId` set to B with `errors[0].code` equal to `Licence.Expired`. This expiry refusal has `retryable: false`. A fresh key at expiry receives HTTP 403. An authorized resend with changed or reordered rows receives HTTP 409 `Operation.PayloadMismatch`. Revoked authority or security suspension withholds the outcome and the hash comparison. An unconfirmed response leaves the original key recoverable.

For unkeyed callers, a proven posting-fence timeout on B also returns 207 when the protected response can be delivered. A retains its original result, and B has `Licence.Busy` with `retryable: true`. Keyed replay contention can conceal a committed outcome, so the response is withheld and the original manifest remains the recovery path.

In the web app, Finish save selects only the interrupted manifest displayed in that tab. If a sibling has replaced it, the page refreshes the draft and waits for another click. Save compares the displayed rows with the durable draft in the same IndexedDB transaction that creates a new manifest. A mismatch refreshes the page without issuing a POST. Adding, editing, removing, clearing and scanner changes use one IndexedDB transaction over the draft and manifest stores. A change is stored only while no manifest is frozen and the stored rows still equal the rows that tab last read or wrote. Otherwise the tab shows the stored draft. A new row is appended after the rows another tab kept, or returned to the form when a manifest is frozen. The draft is available to the current shop's owners and managers. A role refusal withdraws the local details while preserving the stored key and payload. The refusal is kept on the device for that user and shop, so it survives a reload and a cached session that still lists the former role. It ends only when a live `GET /api/shops/me` lists that user as owner or manager of the shop, on page entry or through Check again. Sending a chunk invalidates the original shop's offline stock snapshot even if the response is lost.

Generic gains and unrelated adjustments remain classified as `GeneralStock`. Correction labels do not change that action. A keyed count keeps the `GeneralStock` lease from its posting transaction and reevaluates it, with live session and membership, after its operation receipt is completed. A refusal there rolls back the count, movement, adjustment, quantity change and receipt. A count committed earlier is still returned to an authorized retry of its key. Source receipt corrections continue through their existing `SourceCorrection` endpoint and source eligibility rules.
