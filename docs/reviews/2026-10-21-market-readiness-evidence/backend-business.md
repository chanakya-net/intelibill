# Backend business workflow readiness review

Scope: `/Users/chanakya/projects/intelibill`, backend inventory, sales, returns, credit notes, purchasing, ledgers, offline sync, reporting and exports. Target: Indian retail shops, public SaaS. Read-only static review on 2026-10-21; no production files changed and no test suite run by this reviewer. CodeGraph was used first and throughout; direct reads filled omitted bodies. Test references below describe inspected test code, not a claim those tests passed in this session. Legal/tax compliance must be checked against official sources by the parent reviewer; implementation facts here are not legal conclusions.

## Assessment

The backend is a substantial retail product, not an inventory CRUD prototype. It already contains batch stock, reasoned adjustments and reversal, mixed goods/services sales, configured and instant discounts, returns, store credit, offline invoice leasing and reconciliation records, purchase-order lifecycle and partial receipts, customer/supplier ledgers, and Excel/PDF/Tally exports. Several difficult boundaries are handled well. The blocking weaknesses are specific: partial writes on failed bulk rows, incorrect batch correction accounting, concurrent refund protection, trusted offline arithmetic, and incorrect export accounting. Passing the current suite alone will not close them because some tests intentionally encode the problematic financial behavior.

## Ten strongest findings

### F1 — P1 confirmed defect: failed bulk inbound rows can still commit stock records

**Evidence.** [AddInventoryBatchCommandHandler.cs:62-74](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Inventory/Commands/AddInventoryBatch/AddInventoryBatchCommandHandler.cs:62) continues after row processing errors and finally saves the shared unit of work if any row succeeded. [AddInventoryCommandValidator.cs:29-30](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Inventory/Commands/AddInventory/AddInventoryCommandValidator.cs:29) permits zero `TotalPurchaseCost`. [BatchFactory.cs:53,73,75-88](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Inventory/Services/BatchFactory.cs:53) tracks the new batch and stock movement before trying to create the supplier ledger entry. [SupplierLedgerEntry.cs:61-63](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Domain/Entities/SupplierLedgerEntry.cs:61) rejects a zero amount. [InboundInventoryLineProcessor.cs:33-53](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Inventory/Services/InboundInventoryLineProcessor.cs:33) returns before updating the inventory aggregate when batch factory fails.

**Scenario.** Submit two bulk rows for an existing item: a valid paid receipt, then a second distinct batch with quantity 5 and purchase cost 0. Row 2 is returned as failed, but its added batch and IN transaction are still tracked. The final save for row 1 persists row 2's batch and movement without its item aggregate quantity or supplier ledger entry. Reported failures and database stock disagree. A new-item failed row with an invalid supplier can similarly leave its newly tracked Item behind.

**Fix / acceptance.** Make row processing side-effect-free until valid, or isolate each row with a savepoint/unit of work and restore tracked/cache state on failure. Decide explicitly whether free stock is supported; if supported, omit a zero liability entry. Integration test a valid row plus zero-cost/invalid-supplier row and verify failed row leaves no item/batch/movement/ledger mutations, or succeeds with coherent zero liability under the chosen policy. Also test duplicate item+batch within the same unsaved bulk request: database queries do not see newly added batches.

**Coverage.** Existing partial-success integration test at [InventoryControllerTests.cs:259](/Users/chanakya/projects/intelibill/tests/backend/integration/Intelibill.Integration.Tests/InventoryControllerTests.cs:259) does not establish isolation after a late business-validation failure. Unit tests mock the processor pieces rather than a real change tracker.

### F2 — P1 confirmed defect: downward batch corrections lose their stock audit movement

**Evidence.** [UpdateInventoryBatchCommandHandler.cs:131-145](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Inventory/Commands/UpdateInventoryBatch/UpdateInventoryBatchCommandHandler.cs:131) selects `StockTransactionType.Out` for a negative difference, but passes `Math.Abs(quantityDifference)`. [StockTransaction.cs:85-95](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Domain/Entities/StockTransaction.cs:85) rejects a positive OUT quantity. The handler ignores that error (`if (!transaction.IsError)`) and saves at204.

**Scenario.** Correct batch quantity 10 to 8. Item inventory falls by 2 and old batch is voided/replaced, but there is no OUT movement for the 2. Stock movement audit no longer reconciles to stock balance.

**Fix / acceptance.** Pass signed `quantityDifference`, propagate every transaction creation error, and persist batch replacement/quantity/audit/ledger atomically. Integration test10→8 requires exactly one signed OUT(-2), correct aggregate 8, and a reconstructible correction chain; error injection must leave all state unchanged.

**Coverage.** `InventoryControllerTests.cs:408-493` tests an upward correction10→12 and its payable entries, so it cannot expose the negative-sign branch. Unit correction tests only exercise access/error cases and publish behavior ([UpdateInventoryBatchCommandHandlerTests.cs:39-229](/Users/chanakya/projects/intelibill/tests/backend/unit/Intelibill.Application.Unit.Tests/Features/Inventory/Commands/UpdateInventoryBatch/UpdateInventoryBatchCommandHandlerTests.cs:39)).

### F3 — P1 confirmed defect: correcting a partly sold batch rewrites purchase liability from remaining stock

**Evidence.** [UpdateInventoryBatchCommandHandler.cs:63-64](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Inventory/Commands/UpdateInventoryBatch/UpdateInventoryBatchCommandHandler.cs:63) uses current remaining quantity. It voids/replaces the old batch at80-105, reverses the old full goods-received entry at158-168, then creates liability as `command.Quantity * command.CostPrice` at183-191. There is no check for prior sales or explicit purchase-document correction semantics. A price-only correction skips all ledger transfer because condition153 is false. [InventoryBatch.cs:59,74-78](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Domain/Entities/InventoryBatch.cs:59) resets original quantity on replacement and zeroes the old batch.

**Scenario.** Buy 10 units for 100 each (supplier due 1000), sell 4, then correct the cost of the remaining 6 to 110. Handler reverses 1000 and adds 660: supplier due falls to 660 even though no purchase return/payment occurred. If correcting the original purchase cost, due should 1100; if only revaluing remaining stock, purchase payable should remain 1000. Neither business meaning gives 660. A prior price-only correction leaves the receipt liability on the old batch; a subsequent cost correction on the new batch finds no original receipt and adds a second liability without reversing the original.

**Related confirmed workflow break.** Even a price-only correction voids the original batch. A later return of an earlier sale still points to that original batch; [SaleReturnValidator.cs:103-119](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Sales/Services/Returns/SaleReturnValidator.cs:103) rejects it as voided for restocking. Legitimate earlier purchases become unreturnable as restockable goods after a retail price change.

**Related concurrency risk.** Quantity-unchanged replacements do not update `Inventory` (109-128), the only inventory entity with `xmin` ([ApplicationDbContext.cs:61-67](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Infrastructure/Data/ApplicationDbContext.cs:61)); `InventoryBatchConfiguration.cs` has no token. Two corrections using different new batch numbers can each read the same old batch, void it, and add an active replacement without conflicting. Needs a deterministic integration test before calling this reproduced.

**Fix / acceptance.** Separate price metadata updates, stock-count corrections, and purchase financial corrections. Keep a stable physical batch lineage and immutable receipt liability; use explicit delta entries for purchase corrections. Test post-sale cost correction, successive price/cost edits, old-sale return after price change, and concurrent same-batch correction. Supplier debt must change only by the documented commercial adjustment.

### F4 — P1 confirmed concurrency hole: service/wastage returns can refund more than sold

**Evidence.** [SaleReturnValidator.cs:43-75](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Sales/Services/Returns/SaleReturnValidator.cs:43) reads existing returns and validates remaining quantity before persistence. [RecordSaleReturnCommandHandler.cs:80-81](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Sales/Commands/RecordSaleReturn/RecordSaleReturnCommandHandler.cs:80) skips all stock mutations for service or wastage lines, and184-190 only inserts the return/ledger/credit-note records. [SaleReturnConfiguration.cs:11-16,76-81](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Infrastructure/Data/Configurations/SaleReturnConfiguration.cs:11) checks per-record amounts and return-number uniqueness, not total returned quantity; random return numbers permit distinct concurrent inserts. **Scenario.** Two managers simultaneously return the sole service or wastage unit of a 100 sale. **Fix / acceptance.** Lock or version the sale/return aggregate inside the transaction before reading prior returns and update a concurrency-protected record on every return/void, including no-stock paths. Add command idempotency. Barrier-based PostgreSQL integration tests for service, wastage, restockable and mixed returns and double void: combined active returned quantity cannot exceed sold quantity; each reversal occurs once; losing request is a usable conflict or replay.

**Coverage.** Current integration coverage demonstrates individual wastage and restockable behavior (`SalesControllerTests.cs:3153,3756`) and concurrent credit-note redemption (`3349,3517`), which is a different invariant. No concurrent return test found in that suite.

1. **Customer payment allocation is absent.** Customer payment writes `saleId:null` ([RecordCustomerPaymentCommandHandler.cs:39](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Customers/Commands/RecordCustomerPayment/RecordCustomerPaymentCommandHandler.cs:39)) and never modifies any invoice. ## Suggested release gates for this backend slice

1. Fix F1-F8 and prove invariants with real PostgreSQL integration tests; single-request mock tests cannot prove shared-context isolation, uniqueness or concurrency behavior.
2. Agree one pricing/tax/cost policy and business timezone; implement F9/F10 and the Indian tax-invoice gate for the supported retailer segment.
3. Provide payment correction/allocation and offline review recovery before public users can create unrecoverable money/stock mistakes.
4. Reconcile opening stock + signed movements = current stock by item/batch; supplier receipt/adjustment/payment totals = payable; customer invoices/returns/collections = receivable; every exported accounting voucher balances. Run these against mixed workflows including retries, partial refunds, price corrections after sales, and period boundaries.
5. Keep unsupported capabilities visible in launch scope: advanced GST filing, e-invoicing, multi-tender/till close, supplier returns, inter-shop transfers, invoice settlement allocations and import/migration tools should not be implied by generic "complete retail accounting" claims.
