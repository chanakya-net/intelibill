# Intelibill Angular web readiness review — Indian retail, public SaaS

Scope: Angular web and the contracts it consumes; mobile excluded. Read-only review on 2026-10-21. Source evidence below is current local source, explored through CodeGraph first with direct reads for omitted regions, templates, configuration and graph misses. No code changes or test suites were run by this reviewer. The main reviewer owns build, test and browser verification. Findings are static-confirmed implementation defects unless explicitly marked as a launch gap. WEB-03 was independently reproduced by the main reviewer using the actual production service worker on a local scratch server.

## Assessment

This is a substantial retail application, not a dashboard mockup. It already has usable foundations for product/batch management, mixed goods/services POS, returns, store credit, procurement, customer/supplier accounts, exports, nine languages, and deliberate offline billing. Public launch should wait for identity/shop isolation in browser state, safe sale retry, reliable offline recovery/receipts, and a defined GST invoice scope. These defects are more important than adding more modules.

The strongest positive is that operational exceptions have been considered: partial inbound saves preserve unsuccessful rows, purchase orders have receipt history and lifecycle states, return preview precedes financial mutations, and offline bills keep frozen pricing plus leased invoice numbers. The weakest boundary is preserving the meaning of state when identity, active shop, connectivity or delivery certainty changes.

## Ten strongest prioritized findings

### WEB-01 — P1: A retried online checkout is a new sale

Evidence: [new-sale-page.cart-submit.service.ts:236–237](/Users/chanakya/projects/intelibill/src/frontend/src/app/features/sales/pages/new-sale-page.cart-submit.service.ts:236) calls `createSaleIdempotencyKey()` for every submit. [new-sale-page.discount-actions.service.ts:5–10](/Users/chanakya/projects/intelibill/src/frontend/src/app/features/sales/pages/new-sale-page.discount-actions.service.ts:5) always creates a new UUID/timestamp. Failure action leaves draft available to retry ([sales.effects.ts:139–150](/Users/chanakya/projects/intelibill/src/frontend/src/app/features/sales/state/sales.effects.ts:139)).

Failure scenario: server commits sale and stock/customer ledger effects, but response is lost. Cashier presses submit again; new idempotency key defeats backend duplicate detection. Stock/revenue/debt can be doubled. The submitting guard prevents simultaneous clicks, not an uncertain first result.

Fix: create/persist a checkout-intent key once, retain the same immutable payload/key through uncertain delivery and retries, reconcile prior result before allowing changes/new checkout, clear only on confirmed success or explicit abandonment.

Acceptance: drop first response after successful commit; retry returns the same sale/invoice and exactly one stock/ledger mutation, including reload and offline transition during recovery.

### WEB-02 — P1: Nonempty carts survive shop switches and are persisted into the new shop

Evidence: [new-sale-page.lifecycle.service.ts:154–170](/Users/chanakya/projects/intelibill/src/frontend/src/app/features/sales/pages/new-sale-page.lifecycle.service.ts:154) reloads/persists on activeShopId change. [sale-cart-state.service.ts:33–68](/Users/chanakya/projects/intelibill/src/frontend/src/app/features/sales/services/sale-cart-state.service.ts:33) replaces loaded rows only when the current in-memory cart is empty. `:81–109` writes current rows using the current auth shop ID. Service is root-scoped (`:23`).

Failure scenario: add Shop A item, switch to B while POS remains open. A cart stays in memory, B's saved cart is ignored, and subsequent persistence saves A item IDs as B draft. Selected customer/discount/credit note transient state is also not cleared by the shop-change effect. API may reject foreign IDs, but customer sees wrong shop cart and B draft can be overwritten. Same root cart can survive logout/login in the same SPA.

Fix: bind cart and checkout state to user+shop, synchronously detach old scope before async load, persist old scope explicitly, reject late results, clear customer/credit-note/preview state, and handle logout. Prompt/save before scope changes where work would be lost.

Acceptance: A/B have independent nonempty goods/service carts; switch repeatedly and in another tab, including during async load; each cart, customer and preview belongs to its shop and persisted drafts are unchanged in the other shop. Logout/login as another user never reveals previous cart.

### WEB-03 — P1: Broad authenticated API service-worker cache is not tenant/identity partitioned (runtime confirmed)

Evidence: `src/frontend/ngsw-config.json:55–65` caches `/api/**` for one hour with 8-second freshness timeout. Enabled in production at [app.config.ts:85–88](/Users/chanakya/projects/intelibill/src/frontend/src/app/app.config.ts:85). Auth interceptor changes bearer header only ([auth.interceptor.ts:16–19](/Users/chanakya/projects/intelibill/src/frontend/src/app/core/interceptors/auth.interceptor.ts:16)). Local installed Angular worker falls back via `cache.match(req, cacheQueryOptions)` after timeout (`src/frontend/node_modules/@angular/service-worker/ngsw-worker.js:918–938`, `:979–989`), with age/LRU keyed by URL. No response `Vary: Authorization`, application cache clearing or identity-specific URL partition was found. Logout clears only auth storage/session ([auth-session.service.ts:210–215](/Users/chanakya/projects/intelibill/src/frontend/src/app/core/auth/auth-session.service.ts:210)).

Failure scenario: A's `/api/customers`, `/api/sales?...` or `/api/bank-accounts` is cached; user switches shop or logs out and another user logs in on same browser. If new identity's matching URL times out/offline, old identity's response can be served. Backend RLS cannot protect a response delivered entirely from browser cache.

Fix: remove generic authenticated API caching; keep app assets and the explicit shop-scoped offline snapshot/queue design. If particular caches remain, use deliberate user+shop partition and identity transitions, not URL-only fallback. Server cache headers alone do not replace explicit service-worker policy review.

Acceptance: production SW active, populate A, switch B/new user, delay matching request >8s and disconnect; never render A data. Verify logout purges protected cached content and no cache fallback can reveal it. Main reviewer reproduced this against the actual production `ngsw-worker.js`/`ngsw.json` on a local scratch server: `/api/review-tenant` cached with Authorization Shop-A; requesting the same URL with Authorization Shop-B and delayed network returned `{tenant:"Shop-A"}` after 8,005 ms. Evidence: [saved reproduction result](/Users/chanakya/projects/intelibill/docs/reviews/2026-10-21-market-readiness-evidence/service-worker-cache-result.json); reusable harness: [saved reproduction harness](/Users/chanakya/projects/intelibill/docs/reviews/2026-10-21-market-readiness-evidence/service-worker-cache-probe.mjs). No production API was touched.

## Public SaaS gaps and staged roadmap

These are missing product/business capabilities observed in the web routes and workflows, not necessarily bugs. Prioritize against the launch promise rather than adding every accounting feature.

### Before public onboarding

1. Resolve WEB-01 through WEB-07 and define retail quantity scope (WEB-08). A small pilot must not use duplicate sales, cross-shop state or unresolvable offline bills as feedback mechanisms.
2. Publish terms/privacy/data-handling and clear support/contact, incident/status and recovery routes. [app.routes.ts:5–77](/Users/chanakya/projects/intelibill/src/frontend/src/app/app.routes.ts:5) only exposes auth, print and authenticated shell; login/register/shell templates have no terms/privacy/help/support destinations.
