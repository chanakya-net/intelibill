# API security, authentication and tenancy readiness review

Scope: backend API and supporting authentication/tenancy implementation in `/Users/chanakya/projects/intelibill`; public SaaS for Indian retail shops; mobile excluded. Read-only static review, no test execution or repository modifications. CodeGraph was consulted first; omitted backend source was then read directly. Findings describe code-supported conditions, not a claim that a deployed service was penetration tested. Line references are current workspace source.

## Assessment

The foundation is substantially beyond a prototype: explicit shop membership checks, server-issued shop-scoped JWTs, role-restricted money/inventory operations, password hashing, reset-token hashing, token rotation, database migrations and meaningful negative-path tests exist. Public registration and session lifecycle still have exploitable gaps. Do not open unrestricted signup until the first three findings and identity verification/recovery paths are addressed. Tenant RLS must be validated with the real runtime role before relying on the documented boundary.

## 1. High / launch blocker: email auto-linking enables pre-account takeover

**Evidence.** [RegisterWithEmailCommandHandler.cs:22](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Auth/Commands/RegisterWithEmail/RegisterWithEmailCommandHandler.cs:22) checks uniqueness, stores the supplied password and immediately issues access/refresh tokens through line 44. [User.cs:36](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Domain/Entities/User.cs:36) creates this account without marking its email verified. [ExternalLoginCommandHandler.cs:37](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Auth/Commands/ExternalLogin/ExternalLoginCommandHandler.cs:37) automatically finds an existing account by provider-returned email and links the provider through line 62, without proving control of the old account, clearing its password, or revoking its existing sessions. [LoginCommandHandler.cs:27](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Auth/Commands/Login/LoginCommandHandler.cs:27) accepts the old password; line 33 then loads the user's current shop memberships.

**Scenario.** Attacker registers a prospective customer's email with an attacker-selected password and an unused phone. Later the genuine email owner signs in with Google: the valid Google identity silently attaches to the attacker's pre-created account. The customer creates their shop and enters inventory/customer data. The attacker still knows a valid password for that exact user and can log in to the customer's shop. This does not require forging a Google token or access to the victim's mailbox.

**Fix.** Verify email possession before granting a usable local identity; do not silently merge accounts based solely on an email match. Require an explicit authenticated linking/recovery flow, invalidate pre-verification credentials and sessions when claiming an account, and check provider verification semantics. The same protection must apply to email changes (`UpdateMyProfileCommandHandler.cs:24-45`), not only initial signup.

**Acceptance.** Integration test with attacker registration followed by victim OAuth must never leave the attacker password or pre-claim refresh tokens usable against the victim's resulting account. Test existing verified local accounts, existing external accounts, unverified provider emails and changed email addresses separately.

## 2. High / launch blocker: disabled users and reset sessions can regain indefinite sessions

**Evidence.** [LoginCommandHandler.cs:30](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Auth/Commands/Login/LoginCommandHandler.cs:30) checks `IsLoginEnabled`. [EditShopUserCommandHandler.cs:53](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Users/Commands/EditShopUser/EditShopUserCommandHandler.cs:53) changes it without revoking tokens. [RefreshTokenCommandHandler.cs:19](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Auth/Commands/RefreshToken/RefreshTokenCommandHandler.cs:19) reads a live refresh token and issues a new pair through line 33 without checking the flag. [RefreshTokenRepository.cs:11](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Infrastructure/Repositories/RefreshTokenRepository.cs:11) filters only token revocation/expiry. [ExternalLoginCommandHandler.cs:65](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Auth/Commands/ExternalLogin/ExternalLoginCommandHandler.cs:65) also issues tokens without checking login enablement. JWT validation in [Program.cs:75](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Api/Program.cs:75) checks signature, issuer, audience and lifetime but has no live user/session-version validation.

There is also a recovery bypass: [ResetPasswordCommandHandler.cs:34](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Auth/Commands/ResetPassword/ResetPasswordCommandHandler.cs:34) updates the password and revokes current refresh tokens, but [UpdateMyProfileCommandHandler.cs:20](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Users/Commands/UpdateMyProfile/UpdateMyProfileCommandHandler.cs:20) allows any still-valid access token to obtain a fresh access/refresh pair (lines 40-45), without the old refresh token, current password, login-status or session-version check. Shop creation/switch also mint new pairs.

**Scenarios.** (a) Owner disables an employee; the employee can keep rotating refresh tokens and accessing their retained membership. (b) Customer resets a stolen credential; an attacker holding the old unexpired access token sends `PUT /api/users/me` with the unchanged profile and obtains a new refresh token after the reset. The resulting compromise persists beyond the original access token's expiry, so this is stronger than the usual bounded JWT logout delay.

**Fix.** Centralize user/session validity enforcement for every token-issuing and protected path. Add session/security versioning or a revocable server-side session record, revoke sessions on disable/reset, and require appropriate proof before issuing new refresh credentials from profile/shop operations. Scope employee suspension to a membership rather than global identity where appropriate.

**Acceptance.** After disable, login, OAuth, refresh, profile update, shop creation/switch and protected API calls all reject the old identity/session. After password reset/change, an old access token cannot mint any new refresh credential. Include current and concurrent requests, re-enable behavior, and explicit policy for access-token grace periods.

## 3. High / launch blocker: a shop owner controls another shop's user identity

**Evidence.** [EditShopUserCommandHandler.cs:23](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Users/Commands/EditShopUser/EditShopUserCommandHandler.cs:23) verifies the actor owns the active shop and target is not an owner **in that shop**. At lines 53-54 it changes `targetUser`'s global email/name/phone and login-enabled flag. [User.cs:121](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Domain/Entities/User.cs:121) confirms these are global account fields. [CreateShopCommandHandler.cs:22](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Shops/Commands/CreateShop/CreateShopCommandHandler.cs:22) allows any existing user to create a separate shop and become its owner. Password reset routes mail according to the account's current email ([RequestPasswordResetCommandHandler.cs:21](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Auth/Commands/RequestPasswordReset/RequestPasswordResetCommandHandler.cs:21), lines 36-40).

**Scenario.** A person is staff/manager in shop A and owns a separate shop B. Owner A can change that person's global email to an address A controls and request a password reset, acquiring the identity that owns B. Even without recovery mail, A can globally disable the user and disrupt B. The ownership check on A does not authorize control of B's identity.

**Fix.** Separate global account ownership from shop membership administration. Shop owners should manage invitation, shop-specific role and membership suspension; only the account holder should change verified sign-in/recovery identifiers, with reauthentication and verification. If managed employee identities are intentional, prevent them from independently owning unrelated tenants and define migration to personal accounts.

**Acceptance.** Two independent shops sharing a user: an owner of one cannot change the user's recovery identity, disable access to the other, read unrelated memberships or obtain ownership through password reset. Test staff-in-A/owner-in-B explicitly.

**Evidence.** [20260425075353_InitialCreate.cs:15](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Infrastructure/Migrations/20260425075353_InitialCreate.cs:15) creates core tables including shops, users, bank accounts, customers, items, memberships and sales. The complete migration file contains no RLS policy/enable statements. Repository-wide SQL/C# inspection found policies for newer discount rules, services, purchase orders/receipts, reconciliation and credit-note tables, but none for the original shop-owned tables. An example of the later implementation is [20260510103805_AddDiscountRules.cs:84](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Infrastructure/Migrations/20260510103805_AddDiscountRules.cs:84), which enables/forces RLS and compares `shop_id` to the session shop. [ApplicationDbContext.cs:57](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Infrastructure/Data/ApplicationDbContext.cs:57) also defines no global tenant query filter. [RepositoryBase.cs:14](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Infrastructure/Repositories/RepositoryBase.cs:14) has unscoped generic find/get methods.

Production explicitly installs [PostgresSessionContextInterceptor.cs:10](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Infrastructure/Data/Interceptors/PostgresSessionContextInterceptor.cs:10), assigning parameterized user/shop context on connection open, through [DependencyInjection.cs:51](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Infrastructure/DependencyInjection.cs:51). **Impact/bounds.** The documented blanket RLS boundary is not reproducible from the fresh migration chain. This is not evidence that every current endpoint permits cross-shop access: inspected business handlers usually check current membership and explicitly compare `ShopId` (e.g. [UpdateItemCommandHandler.cs:19](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Items/Commands/UpdateItem/UpdateItemCommandHandler.cs:19), lines 23-35). The same audit found the integration role has `rolsuper=true` and `rolbypassrls=true`; evidence file: `/tmp/intelibill-rls-audit.txt`. This database audit was run by the parent reviewer, not this static-review agent.

**Fix/acceptance.** Inventory every tenant-bearing table, add reviewed idempotent migration policies and separate global identity/bootstrap access where necessary. Run actual runtime-role tests with production session interceptor, `NOBYPASSRLS`, separate migrator role, alternating shops on reused connections, absent context and cross-shop reads/writes. Assert `pg_class.relrowsecurity`/`relforcerowsecurity` and policy coverage after migrating an empty database. Do not count superuser-backed tests as proof of RLS.

## 5. Medium: phone signup creates an unrecoverable passwordless account without proving phone ownership

**Evidence.** [AuthController.cs:46](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Api/Controllers/AuthController.cs:46) accepts only phone/name. [RegisterWithPhoneCommandHandler.cs:21](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Auth/Commands/RegisterWithPhone/RegisterWithPhoneCommandHandler.cs:21) checks uniqueness, then immediately grants tokens without OTP or password. [User.cs:55](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Domain/Entities/User.cs:55) leaves email/password null. Login rejects a null password hash ([LoginCommandHandler.cs:27](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Auth/Commands/Login/LoginCommandHandler.cs:27)); reset requires email and an existing password hash ([RequestPasswordResetCommandHandler.cs:24](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Auth/Commands/RequestPasswordReset/RequestPasswordResetCommandHandler.cs:24)); change-password rejects password-not-set ([ChangeMyPasswordCommandHandler.cs:21](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Users/Commands/ChangeMyPassword/ChangeMyPasswordCommandHandler.cs:21)).

**Scenario.** Anyone can reserve another person's phone number and create shops. A legitimate phone-only registrant can work while refreshing but cannot authenticate again after losing/revoking the session. This is not an existing-account takeover by itself; it is identity squatting, onboarding abuse and a recovery dead end.

**Fix/acceptance.** Implement verified OTP enrollment/login and a recovery path, or disable the public endpoint until it is supported. Test signup→logout→new-device login→lost-session recovery; only verified phone owners may bind a number. Add per-destination quotas and abuse controls rather than relying solely on per-IP request limits.

## 6. Medium: refresh rotation lacks atomic consumption, reuse-family handling and at-rest hashing

**Evidence.** [RefreshTokenCommandHandler.cs:19](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Auth/Commands/RefreshToken/RefreshTokenCommandHandler.cs:19) performs read→revoke tracked object→insert replacement→save. [RefreshTokenRepository.cs:11](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Infrastructure/Repositories/RefreshTokenRepository.cs:11) does a normal active-token query. [RefreshTokenConfiguration.cs:15](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Infrastructure/Data/Configurations/RefreshTokenConfiguration.cs:15) persists the raw bearer token with a unique index and no concurrency/version token; [RefreshToken.cs:5](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Domain/Entities/RefreshToken.cs:5) has no parent/family/session identifier.

**Scenario.** Two requests can both read the same active token before either save and independently persist valid replacement tokens. A stolen token raced against the legitimate client can leave two live branches; replaying an already revoked token rejects that request but cannot revoke the surviving family. Read access to the token table yields directly usable credentials. The race is statically supported; no concurrency reproduction was executed here.

**Fix/acceptance.** Atomically consume one active token (conditional update/row lock plus one transaction), store only a hash, model session/family lineage and a documented reuse response. Barrier-synchronized parallel refresh must produce only one live successor; a stolen/reused predecessor must not leave a live unauthorized branch. Test logout/reset racing refresh.

## 7. Medium: live hubs outlast membership removal and do not check live membership at connect

**Evidence.** [ProductHub.cs:13](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Api/Hubs/ProductHub.cs:13) and [ShopUpdatesHub.cs:13](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Api/Hubs/ShopUpdatesHub.cs:13) join a shop group solely from the signed `active_shop_id` claim, without loading user/membership status. [Program.cs:195](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Api/Program.cs:195) maps hubs without a configured expiration-close option. User/membership edits do not disconnect existing hub connections. Events are sent to the group without reauthorization: [SignalRProductHubNotifier.cs:16](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Api/Services/SignalRProductHubNotifier.cs:16) includes product id/barcode/name; [SignalRShopUpdatesNotifier.cs:16](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Api/Services/SignalRShopUpdatesNotifier.cs:16) includes event type, shop id and changed record ids.

**Fix/acceptance.** Check active membership/status at connect, disconnect on membership/session revocation and bound connection life to token expiry. ## 8. Medium: request throttling is non-atomic and lacks account/destination budgets

**Evidence.** [RateLimitFilter.cs:49](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Api/Middleware/RateLimiting/RateLimitFilter.cs:49) reads a cache count, increments it in process and writes it back at line 70. ## Missing launch capabilities supported by the code inspection

1. **Verified account enrollment and verified email/phone changes**; `IsEmailVerified` exists but is not a usable enrollment gate. Implement ownership proof and anti-squatting recovery before public self-service registration.
2. **Employee invitation/acceptance and account/member separation.** Current owner add-user flow creates a global account with owner-selected password and rejects an existing email ([AddShopUserCommandHandler.cs:39](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Users/Commands/AddShopUser/AddShopUserCommandHandler.cs:39)); it cannot safely invite an existing SaaS identity. Owner-selected credentials should not become a permanent cross-tenant control channel.
3. **Session inventory, per-device/session revocation, revoke-all, and security notifications.** Auth routes expose refresh/revoke of one bearer token and password reset; refresh entity has no device/session lineage. Current password change is the only user-facing bulk revoke route found. Build this on the corrected session model, optionally add stronger owner authentication/MFA according to customer risk.
4. **Complete self-service identity/shop lifecycle.** The users/shops controller surfaces inspected include create/read/update and role/membership editing; no account closure, shop closure/export workflow, ownership transfer or recovery contact process was found. Sales/P&L exports do not by themselves provide a complete customer/shop data portability lifecycle. Define retention/anonymization with the product/legal review rather than simply deleting financial records.
5. **Multi-shop staff/manager access.** Add-user allows multiple shop memberships ([AddShopUserCommandHandler.cs:51](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Users/Commands/AddShopUser/AddShopUserCommandHandler.cs:51)), but switch endpoint and handler require Owner ([SwitchActiveShopCommandHandler.cs:23](/Users/chanakya/projects/intelibill/src/backend/Intelibill.Application/Features/Shops/Commands/SwitchActiveShop/SwitchActiveShopCommandHandler.cs:23)). A regional manager assigned to several stores cannot explicitly switch among them. Resolve the intended product permission model before advertising multi-store staff support.

## Recommended focused regression gates

Before public launch: pre-account takeover chain; disabled-user refresh/OAuth/profile paths; old-access-token-after-reset refresh minting; cross-owner shared identity edits; parallel refresh and revocation races; RLS with restricted runtime principal and alternating pooled connections; hub membership removal/expiry; verified phone signup and later recovery; delivered production reset email; parallel multi-replica auth quotas; error-response secret sentinel.

Existing tests cover basic password-login disablement, ordinary refresh rotation/revoke, invalid OAuth state/provider tokens and shop ownership errors. Those are valuable but do not establish the above adversarial state-transition guarantees. No test suites were run by this reviewer, per assignment.
