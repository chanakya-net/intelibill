# Offline Reconciliation Console Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let merchants identify, recover and audit every unsynced or divergent offline invoice.

**Architecture:** Every offline submission is first stored as an immutable envelope (`OfflineSubmission`), separately from the sale it may become and from the review case (`ReconciliationIssue`, now a versioned case with status, resolution and an event trail). Posting is extracted from the sync handler into a reusable stager, so a reviewer's approval replays the stored envelope through the same pipeline instead of inventing a second one. Cases close only through an allowlisted action (verified replay, verified link, informational acknowledgment, source-linked stock catch-up, or explicit escalation), each idempotent per operation id and checked against the case's row version.

**Tech Stack:** ASP.NET Core 10, Wolverine, ErrorOr, FluentValidation, EF Core/PostgreSQL (xmin row versions, RLS), xUnit + NSubstitute + Testcontainers; Angular 21 signals, PrimeNG, Transloco, Vitest, Bun.

**Spec:** Backlog item 19 "Offline reconciliation console" (pasted brief, 2026-11-03); [market-readiness review](../../reviews/2026-10-21-market-readiness.md) R11; [web evidence](../../reviews/2026-10-21-market-readiness-evidence/web-workflows.md) WEB-07; [business evidence](../../reviews/2026-10-21-market-readiness-evidence/backend-business.md) offline gap 3.

## Global Constraints

- Angular web + .NET API only; mobile excluded.
- Domain ← Application ← Infrastructure ← Api; repository abstractions + `IUnitOfWork` for writes; ErrorOr, no exception-driven business control flow.
- Bun only for the frontend; C# warnings are errors; migrations are applied separately from API startup.
- One migration: `AddOfflineSubmissionReconciliationAudit`. New tenant tables get `ENABLE` + `FORCE ROW LEVEL SECURITY` and the standard `shop_id = NULLIF(current_setting('app.active_shop_id', true), '')::uuid` policy, plus a `TenantPolicyManifest` entry.
- Legacy offline payloads (no `issuedByUserId`, no `calculationVersion`) keep their idempotency hash byte-for-byte.
- No generic edit-price / renumber / delete action. Invoice numbers are never reused or reallocated.
- Rollback disables actions only; it never deletes envelopes, cases, events or invoice ranges.
- New UI copy exists in all nine locale files (`src/frontend/public/assets/i18n/*.json`); `i18n-coverage.spec.ts` enforces it.

## Decisions

1. **Case = `ReconciliationIssue`.** One reason per case (existing rows keep working). New fields: `Status` (`Open=1`, `Escalated=2`, `Resolved=3`; backfilled from `is_resolved`), `InvoiceNumber`, `OfflineSubmissionId`, `Resolution` (the action that closed it), `ResolutionReason`, `LinkedOperationId`, `ResolutionStockTransactionId`, and `Version` (PostgreSQL `xmin`). `IsResolved/ResolvedAt/ResolvedBy` stay and mirror `Status`. Escalated cases are still unresolved: they count as open and can be resolved later.
2. **Envelope = `OfflineSubmission`** (`offline_submissions`): shop, device, clientSaleId, invoiceNumber, `PayloadHash` (the existing `OfflineSaleSyncIdempotencyHasher.ComputeHash` value), `PayloadJson` (the `OfflineSaleSyncCommand` serialized with `JsonSerializerDefaults.Web`, `jsonb`), claimedSoldAt, `ReceivedAt` (first receipt), `Source` (`Sync=1`, `Recovery=2`), `SubmittedByUserId`, `AssertedIssuerUserId?`, `OriginalIssuerUserId?` (verified only), `OriginalLeaseId?`, `RecoveryOperationId?`, `SaleId?`. Unique on `(shop_id, device_id, client_sale_id, payload_hash)`: an identical resend returns the first row (its `ReceivedAt` is the trusted receipt time); a changed payload is a second row. Rows are inserted with `ON CONFLICT DO NOTHING` *before* posting is attempted and are never updated except a one-time `SaleId` link.
3. **Historical lease rule** (`OfflineIssueTimingPolicy`, evaluated in this order against the lease found by `FindReservedRangeAsync`, which ignores expiry, and the envelope's first `ReceivedAt`):
   `claimedSoldAt < lease.ReservedAt` → `IssueTimeBeforeLease`; `claimedSoldAt > receivedAt + 5 min` → `IssueTimeInFuture`; `FiscalYear.ForDate(claimedSoldAt).StartYear != lease.FiscalYearStart` → `IssueFiscalYearMismatch`; `claimedSoldAt >= lease.ExpiresAt` → `IssuedAfterLeaseExpiry`; `receivedAt >= lease.ExpiresAt` → `HistoricalLeaseReviewRequired`; otherwise accept. A plausible clock value never passes on its own: only a first receipt before expiry does. No device-revocation or closed-period model exists yet (backlog 27); both are out of scope and noted in docs.
4. **Issuer attribution.** New queued payloads carry `issuedByUserId` (signed-in user at issue time; included in the hash only when present). Normal sync: absent → legacy behaviour (sale attributed to the submitter, `OriginalIssuerUserId` null = "not recorded"); equal to the submitter → verified issuer; different → held as `IssuerNotSubmitter`. The web client never submits another user's invoices (they wait for that user or go through recovery). `OfflineSubmission.AttributableUserId => OriginalIssuerUserId ?? (Source == Sync && AssertedIssuerUserId is null ? SubmittedByUserId : null)`; a replay with no attributable user is refused (`Reconciliation.ProvenanceUnverified`). A recovered sale's `ActorUserId` and stock `PerformedBy` are the original issuer; `CreatedBy` of movements/ledger, the envelope's `SubmittedByUserId`/`RecoveryOperationId` and the case's `ResolvedBy` record the operators.
5. **Device history (recovery provenance).** An asserted issuer is *verified* for device D when they hold or held a membership in the shop (any status) **and** either reserved a lease on D (`InvoiceLease.ReservedByUserId`, new, prospective) or submitted a `Source=Sync` envelope from D. Never a member → bundle row rejected (`Recovery.IssuerMismatch`). Member without device history → envelope kept, case escalated (`IssuerUnverified`). No issuer at all → envelope kept, case escalated (`ProvenanceUnknown`). Nothing is posted for the last two.
6. **Recovery bundles always open a review** (`RecoveryReviewRequired`) unless an identical sale already exists for the same identity (then the envelope is linked and nothing else happens). Arithmetic (backlog 18) and structure are checked before any case is filed. Recovery requires an active Owner or Manager: that role check is the `RecoverOfflineInvoices` permission (no finer permission model exists). The cashier's access is never restored.
7. **Bundle checksum.** `checksum = lowercase hex SHA-256 of the exact UTF-8 text of the bundle's "invoices" array` (the client builds it with `JSON.stringify`, the server reads it with `JsonElement.GetRawText()`). Format `"intelibill.offline-recovery"`, version `1`, 1–100 invoices, request ≤ 2 MiB. Each invoice is the existing sync request shape plus `issuedByUserId`. Bundles contain no tokens or session data.
8. **Actions** (`ReconciliationActionPolicy.AvailableActions`, owner/manager; staff get only `Escalate` on Open cases they created; resolved cases get none; `Escalate` only from Open):

   | Case | Actions |
   |---|---|
   | `PricingVariance`, `DiscountVariance`, `CustomerVariance` | `AcknowledgeVariance`, `Escalate` |
   | `StockVariance` with item, batch and printed > consumed | `LinkStockCorrection`, `Escalate` |
   | Envelope + code `HistoricalLeaseReviewRequired` / `RecoveryReviewRequired` / `IssuerNotSubmitter` | `RetryHistoricalLease` (only when the envelope has an `AttributableUserId`), `LinkExistingSale`, `Escalate` |
   | Envelope + `Sale.IdempotencyConflict` or `Sale.InvoiceNumberAlreadyUsed` | `LinkExistingSale`, `Escalate` |
   | Everything else (arithmetic, lease not found, timing codes other than the above, legacy held cases without envelope, `ProvenanceUnknown`, `IssuerUnverified`) | `Escalate` |

   - `LinkStockCorrection(linkedOperationId = InventoryAdjustment id)`: same shop, item and batch; `Direction = Increase`; `Reason ∈ {FoundStock, OtherGain}` (a stock count alone is not procurement evidence); not voided; `Quantity ≥ unresolved` (`printed − consumed`); not linked to another case (partial unique index). Effect: batch and inventory `−unresolved`, one `Out −unresolved` movement referencing the sale's invoice number; the original sale and its movements are untouched.
   - `LinkExistingSale(linkedOperationId = sale id)`: sale in shop with the envelope's device + clientSaleId and `RequestHash == PayloadHash` (links envelope and case). For an idempotency-conflict case the linked sale must be the case's sale and must equal an earlier envelope's hash; the conflicting envelope stays unlinked as evidence.
   - `RetryHistoricalLease`: lease still found, attributable user present, then: existing sale with same identity and hash → link (no second sale); invoice number used by another sale → `Sale.InvoiceNumberAlreadyUsed` (case unchanged); else stage the envelope through `IOfflineSalePoster` and commit sale + envelope link + resolution together. A held/rejected staging outcome returns `[Reconciliation.ReplayRejected, inner error]` and changes nothing.
   - `AcknowledgeVariance` is refused for every type outside the three informational ones.
9. **Concurrency and idempotency.** Resolution and recovery run through `IFinancialOperationExecutor` with new `FinancialOperationType.ReconciliationResolution = 7` and `OfflineRecoverySubmission = 8` (replay returns the stored response; a changed payload under the same key → 409 `Operation.PayloadMismatch`). `expectedVersion` stale → 409 `Reconciliation.CaseVersionConflict`; a concurrent commit detected at save (`DbUpdateConcurrencyException`) → the same 409. Another shop's case is invisible under RLS → 404.
10. **Web console** at `/sales/offline-reconciliation` (all roles; actions follow the server's `availableActions`): device queue (Pending/Failed = transport retry; NeedsReview = open its case; other-user invoices = awaiting their cashier), server cases (status filter, paging, detail with frozen invoice, reason, differences, people, audit trail), resolve form, support bundle export (everyone) and import (owner/manager), device hand-off notice. Offline display never claims a resolution: case state is shown only from the last server response.
11. **Release UI audit.** `tests/ui-audit/release/` does not exist in this repository; the browser check is a mocked UI-audit spec (`tests/ui-audit/mock/offline-reconciliation.spec.ts`) following `sales-history.spec.ts`, and the five forced conditions run against real PostgreSQL in the integration suite.

Error codes (all in `Errors.OfflineReconciliation`, file `Errors.OfflineReconciliation.cs`): held-case codes `OfflineReconciliation.{HistoricalLeaseReviewRequired, IssuedAfterLeaseExpiry, IssueTimeBeforeLease, IssueTimeInFuture, IssueFiscalYearMismatch, IssuerNotSubmitter, RecoveryReviewRequired, ProvenanceUnknown, IssuerUnverified}`; resolution `Reconciliation.{CaseNotFound (404), CaseVersionConflict (409), CaseAlreadyResolved (409), ActionNotAllowed (400), ActionForbidden (403), UnknownAction (400), ReasonRequired (400), InvalidStatusFilter (400), LinkedOperationRequired (400), LinkedAdjustmentInvalid (400), OperationAlreadyLinked (409), SaleIdentityMismatch (400), ProvenanceUnverified (409), EnvelopeMissing (409), ReplayRejected (409), ConcurrentChange (409)}`; recovery `Recovery.{BundleInvalid, BundleFormatUnsupported, BundleChecksumMismatch, BundleShopMismatch, BundleEmpty, BundleTooLarge (all 400), LeaseNotOwned, IssuerMismatch (row-level), NotAuthorized (403)}`.

## Review Focus

- RF1 — Sync after lease expiry: reserved day 1, expires day 8, claims day 3, first received day 10 → NeedsReview `HistoricalLeaseReviewRequired`, envelope and invoice number kept, no sale; approval posts once under the same number. *(Task 2 unit, Task 3 integration)*
- RF2 — Same clientSaleId with a changed amount: two envelopes, original sale unchanged, conflict case resolvable only by an authorized link or escalation. *(Task 2 unit, Task 3 integration)*
- RF3 — Printed 5 / consumed 3: original `Out −3` unchanged; FoundStock `+2` adjustment linked → catch-up `Out −2`, batch closes at 0; acknowledgment and stock-count links refused. *(Task 3 integration)*
- RF4 — Retiring a browser with unsynced invoices: records survive sign-out and shop switch, cleanup never removes unsynced records, the export carries a checksum and no tokens, and hand-off reports "not safe" until server receipt or a covering export. *(Task 5)*
- RF5 — Two reviewers or another tenant: same expected version from two operators → one 200, one 409, one effect; another shop → 404 on read and resolve. *(Task 3 integration)*

## Rollout, backfill and rollback

Migration adds tables/columns only; existing `reconciliation_issues` rows get `status` from `is_resolved`, no envelope (`HasOriginalEnvelope = false`, shown as "original envelope not recorded"), and stay resolvable by the actions their type allows (held legacy cases: escalate only).
