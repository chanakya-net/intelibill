# Purchase receiving lots and error recovery

## Objective and scope

Implement the user's supplied “Purchase receiving lots and error recovery Implementation Plan”, refreshed against `f9b26edc77eb8ea825d2aabf63a98670faf735d7` on 7 November 2026. Receiving staff can record several physical lots for one PO line, keep their work after rejection or connection loss, and reconcile an uncertain submission to exactly one committed receipt. Web and API are in scope; mobile remains wire-compatible but receives no new UI.

The October plan referenced backlog items 12, 13, 15, 22, 24 and 31. Those numbers are context, not proof that a dependency shipped. Current owning sources establish the following:

| Dependency | Verified current behavior | Work in this change |
|---|---|---|
| Receipt replay | `IFinancialOperationExecutor` and `operation_receipts` already reserve and commit a business callback plus its response; PO receiving does not use them. Financial-operation lookup currently exposes payment types. | Add one operation type and lookup slug; adapt PO receiving to the existing executor. |
| Intake transaction correctness | Receive handler owns a transaction, takes the posting-period fence before locking the PO and its lines, and saves receipt, batches, stock movements, receipt values and goods-received payable together. Inbound processor and batch factory do not commit independently. | Preserve this boundary; never use bulk intake's per-row executor. |
| Receipt lineage and correction | Receipt lines already store PO line, item, batch and stock-transaction IDs plus quantity/cost/tax snapshots. `PurchaseReceiptValue` links to the receipt line. Retail revisions and cost corrections already operate without replacing sold batches or rewriting original receipt values. | Add client row identity and prove existing immutable lineage survives a sale and a cost correction. |
| Scope transitions | `ShopContextService` has detach/leave hooks, mutation tracking and epochs; `REQUEST_SCOPE` refuses foreign writes and classifies late answers as `StaleScopeError`. | Integrate receiving with these hooks and correlate every result to its initiating scope and operation. |
| Quantity precision | General intake enforces `QuantityPolicy`. The current dialog and both launch pages still close immediately on dispatch. The dialog recreates form rows when `order` changes, disallows repeated PO line IDs, and validates remaining quantity per row rather than per group. Receive effects use `switchMap` without an operation identity. Existing PO draft storage is for the order builder and keyed only by shop; it is not suitable for receiving recovery.

## Contract decisions

1. Keep `POST /api/purchase-orders/{id}/receipts` and its `PurchaseOrderDetailDto` response. Add optional `operationId: UUID` and optional per-row `clientLineId: UUID`. Keep existing field names, notably `taxIncluded` and `purchaseTaxIncluded`. Legacy callers omitting both still work. The new web UI always supplies both.
2. Register `FinancialOperationType.PurchaseOrderReceipt = 13` and slug `purchase-order-receipt`. The executor key is the operation UUID in canonical `D` format. Read-only recovery uses `GET /api/financial-operations/purchase-order-receipt/{operationId}` and the existing lookup DTO/owner-manager authorization. A miss is unresolved, never permission to create a replacement operation.
3. Authorize the actor before replay. With a key, reserve/replay before checking current PO status, remaining quantity or posting period. Only a new posting callback takes the period fence and PO locks. Thus an already committed receipt replays even after the PO becomes Received/Closed or the month closes. Never call `BeginTransactionAsync` inside the executor callback.
4. Hash the target PO plus all business fields, including ordered lot rows and their supplied client IDs, independent tax flags and dates. Trim text as the posting path does, normalize decimal representation, normalize supplied instants to UTC, and retain a null timestamp as null in the hash. Resolve a default timestamp only inside a newly executing callback. Do not hash a generated timestamp, receipt number or server-generated fallback client ID. Same key with changed content is `Operation.PayloadMismatch`, not a second posting.
5. For omitted client IDs, assign each new receipt line its own entity ID as fallback. Reject explicitly empty IDs and duplicate non-null client IDs. Permit repeated PO line IDs. Add nullable `client_line_id`, backfill existing rows from `id`, and add a unique partial index on `(purchase_order_receipt_id, client_line_id)`. New code always writes an ID; null remains accepted for rolling old-server compatibility and maps to `receiptLineId` in responses. No amounts, quantities or existing foreign keys change.
6. Physical lot identity follows the existing database and batch factory: `(shop, item, batchNumber.Trim())`, with ordinal/case-sensitive comparison. Reject repeated identities within the request, even if their dates or costs differ; retain existing active-batch uniqueness behavior. A product barcode may legitimately repeat across lots and is not a lot identity. The PO line fixes the item; barcode input cannot retarget it or create a different item. Do not introduce a new barcode-equality restriction that breaks existing PO receiving behavior.
7. Validate complete grouped quantities under the PO lock before any inbound processor call. Sum in a wide numeric type to avoid integer overflow. Resolve every referenced PO line and its shop-owned item before mutation; verify the item quantity policy. Reject all lots in an over-remaining group with row identities. Validate scalar price/cost/tax values before posting, including independent flags; preserve zero-cost bonus stock and its existing no-payable behavior.
8. Return row errors with stable code, field and client identity/index. Keep public problem envelopes compatible and never expose arbitrary metadata/attempted values. FluentValidation failures already expose property paths such as `Lines[1].Quantity` as their code; map these to the frozen request's client ID in the client. Handler business failures carry whitelisted row metadata projected by the receiving endpoint into additive `rowErrors`. Client translation supplies message keys.

## Durable interaction

Use a dedicated IndexedDB receiving record, keyed by `[userId, shopId, purchaseOrderId]`. Keep editable draft fields and one pending frozen request in the same record/transaction. A successful IndexedDB transaction completion, not an individual request's success event, is the durability boundary before dispatch. Storage unavailable, blocked or failed means show a recoverable storage error and do not send.

Draft states are editing, sending, unknown and confirmed. Sending/prepared records restored after reload are unknown. An unknown record retains exactly the same operation ID, client IDs and serialized payload; editing and creating a new operation stay disabled until resolution. Retry sends the identical payload. Check uses read-only lookup. A matching success or lookup writes a confirmed tombstone before cleanup, preventing a crash or failed delete from resurrecting an editable receipt. A definitive rejection retains editable values, clears the pending request and allows a new identity only on a later submit. Transport loss, timeout, 429, 5xx and stale-scope answers remain unknown. Payload mismatch is retained as unresolved for lookup, not silently replaced. A lookup must match operation key and target before confirmation.

Autosave under the captured owner, flush on dialog close and deliberate scope leave, detach memory on scope changes, and call `beginMutation()` before sending. Release only once the outcome is known or durably recoverable. Late actions cannot clear or close another scope/PO/operation. Recovery must be reachable even when the refreshed order has no receivable lines; otherwise final receipts become impossible to recover through the UI. Read-only confirmed operation responses may contain an older PO snapshot: use them to confirm the receipt, then refresh live PO detail/list rather than treating their status as the latest state.

An authentication/authorization failure while checking or retrying an already-unknown operation does not prove the earlier request failed. Retain the frozen operation so the same owner can reconcile after signing back in or regaining authority. Likewise, a lookup error never converts unknown work into an editable draft. Only a definitive refusal of the keyed command after replay reservation can settle an earlier uncertain submission as rejected.

Use a transaction to prepare/claim the pending request so two tabs do not overwrite an existing unresolved operation with fresh keys. Draft saves must not overwrite a pending/confirmed record. Reject stale draft revisions rather than silently replacing another tab's newer record. On failure keep the current form available; never fall back to a destructive clear.

New lots have stable client IDs and may select the same PO line. Show grouped remaining quantity. Key row helpers and async barcode/tax callbacks by client identity, not mutable indexes; stale callbacks must not overwrite restored/manual/frozen input. Refreshing PO data updates availability without recreating an active form. Receipt history continues to display one row per receipt line and immutable quantity/cost values, with batch navigation and source IDs. Existing batch labels are current batch metadata, not a new immutable historical label snapshot.

## Acceptance and limits

- RF1: rejection retains an editable dialog; uncertain delivery retains an exact replayable request across close/reopen, reload and scope changes.
- RF2: one remaining quantity of 10 accepts lots 4 + 6 as two batches in one receipt; 6 + 6 rejects every affected row without mutation.
- RF3: same-key concurrency/retry/lookup converge on one receipt and payable; competing keys cannot consume the final quantity twice; recovery works after status/period changes.
- RF4: duplicate client identity, duplicate normalized physical lot, foreign PO line/item and invalid cost/tax all reject atomically with usable row errors. A later processor failure rolls everything back.
- RF5: after selling from a lot and applying an existing receipt-cost correction, original receipt line IDs, received quantities, costs and links remain; history shows both lots. Supplier-return behavior is explicitly not claimed.

No external deployment is part of implementation. Apply the additive migration before new API pods, then roll out the web UI. Once new operations exist, rollback must retain a server able to replay/lookup them; hiding the new UI is safe, deploying pre-replay server code behind active pending operations is not. Do not drop lineage or operation receipts on rollback.
